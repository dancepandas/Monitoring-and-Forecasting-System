# 智能体 24 小时连续监测与研判方案

## 1. 需求概述

让 FloodMind 智能体从"被动问答"升级为"主动值班员"：

- **主动监测**：7×24 不间断扫描测站水位、流量、设备状态与数据质量。
- **自动预警**：命中阈值或数据异常时，自动生成分级预警/告警。
- **即时推送**：将关键告警通过企业微信/钉钉/邮件/短信等渠道推送给指定人员。
- **视频联动**：遇到超高水位、超大流量或数据突变时，自动拉取对应时段视频，让 LLM/视觉模型判断是传感器异常还是真实险情。
- **智能研判**：结合历史数据、预报结果、视频证据，给出处置建议并持续跟踪。

## 2. 设计原则

1. **不破坏现有交互**：Agent 对话、前端页面、定时任务保持可用；新增能力以"后台值守"形式并行运行。
2. **可配置、可关闭**：推送渠道、联系人、监测开关、阈值均落到配置文件，管理员可随时调整。
3. **避免告警风暴**：同类事件合并、分级防抖、重复告警去重。
4. **降级兜底**：LLM/视频服务不可用时，仍能保证基础阈值告警和原始数据推送。

## 4. 核心模块设计

### 4.1 监测巡检引擎 `MonitorEngine`

新增文件建议：`gateway/services/monitor_engine.py`

职责：
- 维护一个全局单例，由 `gateway/server.py` lifespan 启动。
- 通过 APScheduler 注册两类任务：
  - `monitor_tick`：高频巡检，默认每 5 分钟执行一次。
  - `video_review`：针对已触发告警的事件，在 1~5 分钟后拉取视频做二次复核。
- 读取 `monitor_config.json` 决定监测站点、联系人、推送开关。

伪代码：

```python
class MonitorEngine:
    def __init__(self):
        self._scheduler = None
        self._alert_tracker = AlertTracker()   # 告警去重与生命周期
        self._contact_book = ContactBook()     # 联系人配置
        self._push_router = PushRouter()       # 推送路由

    def start(self, scheduler: AsyncIOScheduler):
        scheduler.add_job(self._tick, trigger=CronTrigger(minute="*/5"), id="monitor_tick")
        scheduler.add_job(self._video_review_loop, trigger=CronTrigger(minute="*/1"), id="video_review")

    async def _tick(self):
        for code in settings.station_codes.split(","):
            # 1. 数据质量检查
            await self._check_data_quality(code)
            # 2. 水文阈值检查
            await self._check_thresholds(code)
            # 3. 数据突变检查
            await self._check_spike(code)
```

### 4.2 告警事件模型

新增文件建议：`gateway/services/alert_tracker.py`

每个事件至少包含：

```python
class AlertEvent:
    id: str                 # alert_{station}_{type}_{hash}
    station_code: str
    alert_type: str         # level_red / flow_orange / cache_stale / data_spike / video_doubt
    level: str              # 提示 / 蓝色 / 黄色 / 橙色 / 红色
    title: str
    message: str
    metric: dict            # {value, threshold, unit}
    triggered_at: float
    acknowledged: bool
    resolved_at: float | None
    evidence: dict          # 视频截图/LLM复核结论/相关数据
    notify_count: int
    last_notify_at: float
```

**去重策略**：
- 同一站点、同一类型、同一级别在 30 分钟内不重复新建事件，只更新 `notify_count` 和 `last_notify_at`。
- 升级时（如黄色→橙色）立即产生新事件并推送。
- 降级或恢复时，发送"告警解除"通知。

### 4.3 通知路由 `PushRouter`

新增文件建议：`gateway/services/push_router.py`

支持渠道：
- 企业微信（webhook / 应用消息）
- 钉钉机器人
- 邮件（SMTP）
- 短信（预留接口，可接入阿里云/腾讯云）
- 系统内消息（写入前端可拉的 `push_log.json`）

路由规则：
- 红色/橙色告警 → 推送值班员 + 负责人 + 管理员
- 黄色告警 → 推送值班员 + 负责人
- 提示级系统异常 → 仅推送管理员
- 可配置"免打扰时段"，非紧急告警在时段内合并为摘要。

消息模板示例（企业微信 Markdown）：

```markdown
## 🚨 红色预警 — 仙桃站水位超警
**站点**：00106 仙桃站  
**指标**：水位 **36.82 m** ≥ 红色阈值 36.0 m  
**时间**：2026-06-22 16:30  
**视频复核**：已拉取 16:28 视频，LLM 判断为真实水位上涨，非传感器异常。  
**建议**：启动防汛Ⅳ级响应，加密监测频次。  
[查看详情](http://x.x.x.x/agent?alert=xxx)
```

### 4.4 视频联动与 LLM 复核

新增文件建议：`gateway/services/video_review.py`

触发条件：
- 水位/流量达到橙色或红色预警
- 数据出现可疑跳变（相邻时段变化幅度 > 阈值）
- 用户/管理员主动要求复核

执行流程：
1. 根据告警时间，调用 `aiflow_client.get_camera_info(device_code)` 获取摄像头信息。
2. 调用萤石云 API 获取告警时刻前后 30 秒的视频片段（FLV/HLS）。
3. 抽取关键帧（若视觉模型可用）或直接描述视频 URL。
4. 构造 Prompt 让 LLM 判断：
   - 画面是否可见明显洪水、漂浮物、设备遮挡、人为干扰？
   - 与历史同期视频对比，判断是传感器异常还是真实水情。
5. 将结论写入 `AlertEvent.evidence`。

降级：若视频服务不可用，事件仍生成，但标注"待视频复核"。

### 4.5 智能体主动处置工作流

新增 agent 工具：
- `trigger_alert_push(station_code, alert_type, level, message, contacts)`：手动触发一次告警推送。
- ` acknowledge_alert(alert_id)`：人工确认告警。
- `resolve_alert(alert_id, resolution)`：人工关闭并记录处置结果。
- `set_monitor_config(...)`：动态调整监测规则。
- `list_active_alerts()`：查看当前未解除告警。

新增智能体 Prompt 段落（注入 `_SYSTEM_PROMPT`）：

```
## 主动值守能力
- 当系统出现红色/橙色水文预警、数据长时间中断、数据异常跳变时，智能体会自动推送告警给配置的联系人。
- 你对告警有确认、解除、追加说明的权限；也可手动触发一次推送。
- 如用户询问"刚才的告警处理了吗"，应调用 list_active_alerts 查看未关闭事件并汇报。
```

## 6. 实施路线图

### 第一阶段：基础值守（1~2 天）
- [ ] 新建 `monitor_engine.py` + `alert_tracker.py`
- [ ] 接入 APScheduler 每 5 分钟执行一次阈值与数据质量巡检
- [ ] 复用 `warning_config.py` 的阈值规则，自动生成事件并去重
- [ ] 新增 `/api/monitor/alerts` 接口，前端可查看当前告警列表
- [ ] 新增 `list_active_alerts` / `acknowledge_alert` / `resolve_alert` 三个 agent 工具

### 第二阶段：通知推送（2~3 天）
- [ ] 新建 `push_router.py`，先实现企业微信 webhook 和邮件两种渠道
- [ ] 实现 `monitor_config.json` 的读取与热更新
- [ ] 告警事件按联系人配置路由推送
- [ ] 新增 `/api/monitor/config` 和 `/api/monitor/contacts` 管理接口
- [ ] 前端增加"告警规则"和"联系人"配置页

### 第三阶段：视频联动（3~5 天）
- [ ] 新建 `video_review.py`，封装"告警时刻→取视频 URL→抽帧→LLM 复核"流程
- [ ] 接入萤石云/设备摄像头接口（复用 `aiflow_client.get_camera_info`）
- [ ] 橙色/红色告警触发后 1~5 分钟自动执行视频复核
- [ ] 将复核结论写入告警证据并追加到推送消息

### 第四阶段：闭环与自治（5~7 天）
- [ ] 智能体根据告警级别自动推荐处置措施并生成简报
- [ ] 支持定时日报/周报中自动汇总未关闭告警
- [ ] 支持用户通过自然语言查询"最近有什么告警"
- [ ] 增加告警处置反馈，形成"监测→告警→复核→处置→归档"闭环

## 7. 关键时序

```
APScheduler(每5分钟)
       │
       ▼
MonitorEngine._tick
       │
       ├── 读取 data_cache 最新水位/流量
       │
       ├── 对比 warning_config 阈值
       │
       ├── 检测到 00106 水位红色预警
       │
       ▼
AlertTracker.create_or_update
       │
       ├── 生成 alert_id：alert_00106_level_red_202606221630
       │
       ├── 检查 30 分钟内是否已有同类事件 → 若无则新建
       │
       ▼
PushRouter.dispatch
       │
       ├── 匹配联系人（值班员 + 负责人）
       │
       ├── 组装 Markdown 消息
       │
       └── 企业微信 / 邮件并发推送
       │
       ▼
VideoReview.schedule_review（异步，1分钟后）
       │
       ├── 拉取 16:28~16:32 视频
       │
       ├── 抽帧 → 调用视觉 LLM
       │
       └── 结论：真实水位上涨 / 传感器异常
       │
       ▼
AlertTracker.update_evidence
       │
       ▼
PushRouter.push_update（仅内容升级时补充推送）
```

## 8. 风险与降级

| 风险 | 降级策略 |
|------|----------|
| LLM 服务不可用 | 阈值告警仍正常推送，视频复核结论改为"待 LLM 复核" |
| 视频服务不可用 | 告警仍生成，推送中标注"视频待复核"，并建议人工查看 |
| 推送渠道失败 | 记录 `push_log.json`，管理员可在前端查看未送达记录 |
| 数据缓存持续为空 | 每 30 分钟合并为一条"数据缓存异常"告警，避免刷屏 |
| 网络抖动导致误报 | 引入"连续 2 个 tick 命中阈值才触发红色告警"机制 |

## 9. 预期效果

- 红色/橙色水情在 5 分钟内触达值班人员。
- 数据中断类异常 10 分钟内自动推送，并附带排查建议。
- 高危事件自动关联视频证据，减少人工现场核验成本。
- 智能体可 24 小时值守，用户次日只需查看"告警日报"即可掌握夜间态势。

## 10. 下一步待确认

1. **推送渠道优先级**：先做企业微信 webhook，还是钉钉，还是邮件？
2. **联系人/值班表**：是否需要按时间段配置不同值班员？
3. **视频复核模型**：是否已有可用的视觉 LLM（如 qwen-vl-max），还是先用普通 LLM 分析视频 URL/截图文字描述？
4. **部署环境**：网关当前部署在内网还是公网？推送 webhook 能否直接访问外网？
5. **权限范围**：智能体是否允许自动推送，还是每次都需要用户/管理员确认后再发送？
